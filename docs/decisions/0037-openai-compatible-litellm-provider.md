# ADR-0037: Second model provider — OpenAI-compatible (LiteLLM proxy)

## Context

Until now Isolinear speaks only to Ollama's native `/api/chat`
(`MODEL_PROVIDER_OLLAMA_COMPATIBLE`, the sole member of
`SUPPORTED_MODEL_PROVIDER_TYPES`). The homelab is moving local model access
behind a **LiteLLM proxy** that exposes an OpenAI-compatible API
(`/v1/chat/completions`) and can forward to POE-hosted cloud models — which
makes A/B'ing models (the recurring lever behind the codegen prompt-rule work)
a config change instead of a code change. We want Isolinear to route through
it, and to make it the **default for local dev/testing**.

The open question ([[litellm-openai-provider]]) was whether the ADR-0025 live
"thinking" stream survives the move — it is Ollama-specific today (request
`think:true`; response reads `message.thinking` from an NDJSON stream). We
**probed the live proxy** before deciding (per the verify-against-the-real-
pipeline discipline). Findings against `http://10.0.1.39:4000/v1`, model
`ollama/gemma` → `gemma4:e4b`:

1. `/v1/models` exposes `ollama/gemma` and `ollama/qwen-coder`.
2. `response_format: {type: "json_schema", json_schema: {…, strict: true}}`
   returns clean schema-valid JSON through the `ollama_chat` route — the
   planner's structured-output contract holds.
3. Streaming returns the reasoning trace as `choices[0].delta.reasoning_content`
   when `reasoning_effort` is set.
4. **Crucially, reasoning and structured JSON coexist in ONE streaming call:**
   `stream:true` + `response_format:{json_schema}` + `reasoning_effort` yields
   both `delta.reasoning_content` deltas AND a valid structured `content`.
   Ollama could not do this (it suppresses thinking under `format`, forcing the
   two-pass think-then-format design in `plan_chart`/`select_entity`); the
   OpenAI-compatible path does not need the workaround.

## Decision

Add a second model-provider type, **`openai_compatible`**, and make it the
default. Isolinear keeps the Ollama client unchanged; the new provider is a
sibling client selected by `model_provider_type`.

1. **Transport.** POST `{base_url}/chat/completions` (base URL includes the
   `/v1`). Messages are already `[{role, content}]` on both paths — only the
   endpoint, the structured-output field, the streaming wire, and the reasoning
   trigger differ.

2. **Structured output.** Use `response_format: {type: "json_schema",
   json_schema: {name, schema, strict: true}}` where Ollama used `format`. The
   PlannerResult / entity-selection JSON Schemas are reused unchanged.

3. **Reasoning stream (ADR-0025 preserved, simplified).** A single streaming
   call carries both the reasoning and the structured/free content. Parse the
   **SSE** stream (`data: {…}` lines, `[DONE]` terminator); accumulate
   `choices[0].delta.reasoning_content` → the existing `on_reasoning` callback
   (sanitized, exactly as today), and `choices[0].delta.content` → the assembled
   message. Reasoning is requested with `reasoning_effort` (default `"low"`;
   only sent when a reasoning trace is wanted, i.e. when `on_reasoning` is
   provided). The two-pass think/format split is **not** used on this path — one
   streaming call replaces it. A model that returns no `reasoning_content`
   (non-reasoning models / cloud models that hide it) degrades to the same
   ADR-0025 D6 "nothing shown" fallback, unchanged. When `on_reasoning` is None
   a single non-streaming call is made (`stream:false`, no `reasoning_effort`).

4. **Auth (optional bearer, ADR-0032 posture).** The proxy uses
   `Authorization: Bearer <key>` (a LiteLLM virtual/master key). The key is
   **deployment configuration, never generated by the integration** — mirroring
   the ADR-0032 worker token: a write-only options-flow field whose value lands
   in an integration-owned HA `Store`, never in config-entry data or options, so
   the `config_schema.py` secret-vocabulary fail-closed check stays intact and
   the key is never surfaced back to the card. It is **optional** — auth may be
   disabled on the proxy (as it is during initial dev), and cloud/POE routing
   later just needs the key pasted. Absent key ⇒ no `Authorization` header.

5. **Defaults (dev/testing).** `default_config_data()` becomes:
   `model_provider_type: "openai_compatible"`,
   `model_endpoint_url: "http://10.0.1.39:4000/v1"`,
   `planner_model: "ollama/gemma"`, `codegen_model: null` (defaults to the
   planner model — gemma — preserving current codegen behavior; `ollama/qwen-
   coder` is available to set later). The model strings are LiteLLM model ids,
   passed through verbatim as the `model` field.

6. **Ollama retained.** `ollama_compatible` stays a supported type with its
   existing native client and two-pass reasoning; selecting it is unchanged.

7. **In-place provider switch.** `model_provider_type`, `planner_model`, and
   `codegen_model` are surfaced in the **options** form (they live in
   config-entry data, routed there like the editable endpoints — ADR endpoint
   edits, 2026-07-04). An existing install can therefore switch Ollama → the
   LiteLLM proxy without deleting the integration and re-entering its entity
   allowlist; the model-provider client is rebuilt live on submit.

## Consequences

- **Positive.** Model A/B (local vs POE cloud) becomes config-only. The
  thinking stream is preserved and its planner/entity-select path *simplifies*
  to one call. No change to the card/reasoning-surface contract (ADR-0025),
  the grounding gate, the sandbox, or schemas. Additive: `ollama_compatible`
  users are unaffected.
- **Negative / risk.** A second transport + SSE parser to maintain. Structured
  output and reasoning exposure are backend-dependent through the proxy — proven
  for `ollama/gemma` here, **not** guaranteed for arbitrary POE-forwarded cloud
  models (some hide reasoning, some vary on `response_format`); those are opt-in
  per model and degrade gracefully (no reasoning shown; structured-output
  failures surface through the existing planner-validation gate). The proxy is a
  new network dependency for the default path (the internal LAN route is the
  default, so dev is unaffected when the proxy is down only if the user points
  back at Ollama).
- **Out of scope here.** Per-role keys, model-capability discovery, and any
  cloud-model-specific reasoning quirks — demand-driven follow-ups.

## Alternatives considered

- **Refactor the Ollama client into a transport strategy.** Rejected for now:
  it churns the proven native path for no user-visible gain. The two clients
  share the module-level prompt/schema/request-projection helpers; only the
  ~4 transport methods differ. Revisit if a third provider appears.
- **Keep two-pass reasoning on the OpenAI path.** Rejected: probe #4 shows one
  streaming call carries both, so the workaround is unnecessary complexity here.
- **Store the key in config-entry data like the endpoint URL.** Rejected: it is
  a secret; it must follow the ADR-0032 write-only Store posture and the
  secret-vocabulary fail-closed guard.
